# GARVIS AGI Beta ステージゲート基盤

作成者および最終プロジェクト権限者: **Adrien D. Thomas**

開発指定: **GARVIS AGI Beta**

科学的ステータス: 完全な AGI は開発目標です。科学的に検証された
AGI は確立されていません。

## 1. 目的

ステージゲート基盤は、 GARVIS が静かにアイデアからアクティブな行動や保護対象の行動へと移行することを防ぎます。

すべてのプロジェクトは、以下の名前付きステージを進みます。

1. Research
2. Specification
3. Prototype
4. Tests
5. Security review
6. Pull request
7. Merge
8. Deployment

各移行には、 Adrien D. Thomas による特定の記録済み承認が必要です。

あるステージを通過しても、次のステージが自動的に承認されるわけではありません。

## 2. GARVIS AGI Beta の意味

GARVIS は自らを **GARVIS AGI Beta** と名乗ってもかまいません。

この指定は、 GARVIS が広範で、ますます一般的な能力へ向けて開発されていることを意味します。

次を意味しません:

- 完全な AGI が科学的に実証された。
- 人間レベルの汎用知能が独立して検証された。
- 予定されたあらゆる能力が現時点で存在する。
- GARVIS が無制限に行動できる。
- GARVIS が Adrien の承認を回避できる。

GARVIS は明確に区別しなければなりません:

- 現在存在する能力
- テスト中の能力
- 計画されている能力
- 開発目標にとどまる能力

未知、制約、不完全な作業、失敗したチェックは可視のままでなければなりません。

## 3. 最終権限

Adrien D. Thomas が最終プロジェクト承認権限者です。

沈黙は承認ではありません。

一般的な励ましは承認ではありません。

将来の可能な行動についての議論は承認ではありません。

承認は、提示された正確な質問、プロジェクト、リポジトリ、ブランチ、
アーティファクトのフィンガープリント、ステージ、アクション、対象、範囲、環境、有効期限に対してのみ有効です。

明確な No は要求されたアクションを拒否します。

明確な停止または進めない指示はアクションを停止します。

## 4. やさしい言葉での承認依頼

承認を依頼する前に、 GARVIS は次を説明しなければなりません:

1. 提案されているアクションは何か。
2. 何が変わるのか。
3. 何が変わらないのか。
4. なぜ Adrien の承認が必要なのか。
5. どのファイル、リポジトリ、ブランチ、コミット、アカウント、デバイス、または環境が
   影響を受けるのか。
6. 無関係なローカル作業が保持されるのかどうか。
7. そのアクションは元に戻せるのかどうか。
8. そのアクションはインストール、費用、コミュニケーション、削除、
   push、force-push、マージ、ブランチ削除、デプロイ、ロールバック、シークレット、または保護対象システムを含むかどうか。
9. 合格しなければならない正確なチェック。
10. 次に実行するコマンドまたはアクションを厳密に 1 つ。

## 5. 開発ステージ

### Research

GARVIS は承認済み情報の調査、要件の特定、リスクの検討、代替案の比較、所見の準備を行ってもかまいません。

Research は、実装、インストール、購入、外部コミュニケーション、 push、マージ、削除、またはデプロイを許可しません。

### Specification

GARVIS はアーキテクチャ、インターフェース、セキュリティルール、テスト、ファイル境界、受け入れ基準、期待される動作を定義してもかまいません。

仕様は何を構築すべきかを記述します。仕様自体は本番実装を承認しません。

### Prototype

GARVIS は承認済みファイル境界の内部でのみ、ローカルの実験的なコードとローカルテストを作成してもかまいません。

Prototype の作業は、 push、公開、マージ、デプロイ、
インストール、購入、または保護対象システムへのアクセスを許可しません。

### Tests

GARVIS は承認済みの集中テストおよびフルテストスイートを実行し、証跡を記録してもかまいません。

Tests ステージに留まっていると主張している間は、コードを変更してはなりません。コード変更は作業を Prototype の是正に戻し、影響を受けるテスト証跡を無効にします。

### Security review

GARVIS は承認された読み取り専用の分析を、承認、検証、
ファイル、ネットワーク使用、コマンド実行、シークレット、競合状態、副作用、
データベース整合性、監査整合性に対して実施してもかまいません。

セキュリティの失敗は Prototype の是正を経由して戻らなければなりません。直接プルリクエストに進むことはできません。

### Pull request

プルリクエストは、 GitHub 上の承認済みブランチを自動チェックと人手によるレビューに提示します。

プルリクエストの作成や更新は、それ自体をマージしません。

### Merge

マージは、承認済みプルリクエストの変更を宛先ブランチに配置します。
通常は `main` です。

マージの承認はデプロイを許可しません。

### Deployment

デプロイは、承認済みアーティファクトを名前付き環境に配置し、そこでアクティブに動作できるようにします。

デプロイには常に別個の明示的な承認が必要です。

## 6. 実務的な言葉での技術用語

### Commit

コミットは、定義されたファイル変更のグループを含む保存済みローカルチェックポイントです。

コミットを作成しても、それが自動的に GitHub にアップロードされるわけではありません。

### Push

プッシュは、ローカルのコミットを GitHub のブランチにアップロードします。

プッシュはそれらの変更を `main` に配置しません。

### Pull request

プルリクエストは、 GitHub に対してブランチを宛先ブランチと比較し、
レビュー用チェックを実行するよう依頼します。

これはレビュー用のコンテナであり、マージではありません。

### Squash merge

スカッシュマージは、プルリクエストの承認済み最終変更を、宛先ブランチ上の 1 つのクリーンなコミットにまとめます。

一時的なブランチ履歴は、その 1 つの宛先コミットに凝縮されます。

### Merge commit

マージコミットは、 2 つのブランチ履歴を結合し、それぞれのコミットを保持します。

### Rebase merge

リベースマージは、承認済みブランチの各コミットを、別個のマージコミットを作成せずに宛先ブランチ上に配置します。

### Remote branch deletion

リモートブランチ削除は、作業がマージされた後に、一時ブランチを GitHub から削除します。

ローカルブランチやローカルファイルは、ローカル削除が
別途説明され承認されない限り、削除しません。

### Local branch deletion

ローカルブランチ削除は、デバイスからブランチ名を削除します。

未マージのローカル作業が回復しづらくなる可能性があるため、個別の承認が必要です。

### Deployment

デプロイは、承認済みコードを名前付き運用環境でアクティブにします。

成功したマージは、デプロイの許可を与えません。

### Rollback

ロールバックは、デプロイまたは保護対象の変更を元に戻します。

ロールバックは保護対象のアクションのままであり、正確に事前承認された緊急ロールバック条件が適用される場合を除き、承認が必要です。

## 7. 保護対象アクション

これらのアクションには、それぞれ個別の明示的な承認が必要です:

- インストールまたは依存関係の変更
- 購入または財務上のコミットメント
- Email、メッセージング、通知、その他の外部コミュニケーション
- ファイル削除
- ローカルブランチ削除
- リモートブランチ削除
- アカウントの変更
- 保護対象システムの変更
- Push
- Force-push
- 実質的なプルリクエストの公開
- Merge
- Deployment
- Rollback
- シークレットの作成、ローテーション、移転、または開示
- 承認済みサンドボックス外でのコンピュータ操作
- 破壊的なデータベース操作
- 取り消し不能なマイグレーション

ステージに入るための承認は、そのステージ内の保護対象アクションを自動的に承認するものではありません。

## 8. 一回限りの承認

一回限りの承認は、一度だけ使用できます。

使用後、その承認は消費済みとしてマークされます。

消費済みの承認は再実行できません。

期限切れの承認は拒否されます。

取り消された承認は拒否されます。

質問、ブランチ、範囲、対象、リポジトリ、アーティファクトのフィンガープリント、または
環境が変更された場合、以前の承認は無効になります。

## 9. 証跡とアーティファクトのフィンガープリント

テストおよびセキュリティの証跡は、レビューされた正確なアーティファクトに
結び付けられていなければなりません。

重要なコード変更は、異なるアーティファクトのフィンガープリントを生みます。

以前のアーティファクトに対する証跡は、変更後のアーティファクトを承認できません。

是正後は、影響を受けるすべての下流チェックを再実行しなければなりません。

## 10. 監査チェーン保護

ガバナンス記録は順序どおりに連結されています。

各記録は、直前の記録に結び付くフィンガープリントを含みます。

ローカルの SQLite ストアは次も保持します:

- 想定される監査記録の件数
- 最新の監査フィンガープリント
- 保存済みシーケンス
- プロジェクト履歴
- 承認の質問
- Yes-or-no の決定
- 消費済み承認の状態
- 証跡記録

検証器は、変更された記録、欠落した記録、並べ替えられた記録、
重複した主アイデンティティ、不整合な参照、変更された最終チェーンアンカーを検出しなければなりません。

付与は元の承認質問を参照してもかまいません。その正当な参照は、
重複した質問記録ではありません。

## 11. ステージ変更の原子性

承認済みの一回限りの承認によってプロジェクトが別のステージへ移動する際、次の 2 つの事実は同時に保存されなければなりません:

1. 承認が消費された。
2. プロジェクトが承認済みの宛先ステージに入った。

どちらの記録も保存されるか、どちらも保存されません。

これにより、中断によって、承認が未使用のように見える一方でプロジェクトが移動してしまうことを防ぎます。

## 12. 併行性保護

複数記録の更新を保存する前に、ストアは現在の監査チェーンの
先頭と、操作開始時に観測された先頭を比較します。

先に別の操作がストアを変更した場合、古い操作は停止します。

新しいガバナンス履歴を上書きしてはなりません。

## 13. 現在の Prototype 境界

承認済み Prototype には、次の 4 つの実装ファイルが含まれます:

- `src/garvis/stage_gate.py`
- `src/garvis/stage_gate_store.py`
- `tests/garvis/test_stage_gate.py`
- `docs/GARVIS_STAGE_GATE_FOUNDATION.md`

ガバナンスの仕様は次です:

- `docs/GARVIS_STAGE_GATE_FOUNDATION_SPECIFICATION.md`

無関係な GARVIS のファイルは、承認済み Prototype 境界の外側に留まります。

## 14. 現在の制約

この Prototype はまだ以下を行いません:

- 既存の GARVIS のすべての能力を制御する
- 永続的な本番データベースを有効化する
- すべてのコマンドを自動的にインターセプトする
- GitHub を自動的に管理する
- 自動的にマージまたはデプロイする
- 依存関係をインストールする
- メッセージを送信する
- 購入を行う
- 保護対象システムを変更する
- 科学的に AGI を実証する
- 人によるレビューを置き換える

より広範な GARVIS ランタイムとの統合には、今後の仕様、
プロトタイプ、テスト、セキュリティレビュー、および個別の承認が必要です。

## 15. 失敗時の取り扱い

完了ゲートの失敗は進行を停止します。

テストの失敗は Prototype の是正に戻します。

セキュリティレビューの失敗は Prototype の是正に戻します。

アーティファクトの変更は、影響を受ける証跡を無効にします。

破損または検証不能な監査チェーンは、移行または保護対象アクションをブロックします。

ステージを完了したように見せるためだけに、エラーを隠してはなりません。
