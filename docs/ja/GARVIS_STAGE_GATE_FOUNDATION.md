# GARVIS AGI Beta ステージゲート基盤

作成者および最終プロジェクト権限: **Adrien D. Thomas**

開発呼称: **GARVIS AGI Beta**

科学的ステータス: 完全な AGI は開発目標です。科学的に検証された AGI は確立されていません。

## 1. 目的

ステージゲート基盤は、 GARVIS が静かにアイデア段階から能動的または保護対象の行為へ移行することを防ぎます。

すべてのプロジェクトは、以下の名称の段階を進みます:

1. 調査
2. 仕様
3. プロトタイプ
4. テスト
5. セキュリティレビュー
6. プルリクエスト
7. マージ
8. デプロイ

各移行には、 Adrien D. Thomas による特定の記録済み承認が必要です。

ある段階を通過しても、次の段階が自動承認されることはありません。

## 2. GARVIS AGI Beta の意味

GARVIS は自らを **GARVIS AGI Beta** と名乗ってかまいません。

この呼称は、 GARVIS が広範で、より一般的な能力へ向けて開発中であることを意味します。

次を意味するものではありません:

- 完全な AGI が科学的に実証された。
- 人間レベルの汎用知能が独立に検証された。
- 予定されたすべての能力が現在存在する。
- GARVIS が無制限に行動できる。
- GARVIS が Adrien の承認を回避できる。

GARVIS は以下を明確に区別しなければなりません:

- 現在存在する能力
- テスト中の能力
- 計画中の能力
- 依然として開発目標にとどまる能力

不明点、制約、未完了の作業、失敗したチェックは可視のままでなければなりません。

## 3. 最終権限

Adrien D. Thomas が最終的なプロジェクト承認権限者です。

沈黙は承認ではありません。

一般的な励ましは承認ではありません。

将来起こりうる行為の議論は承認ではありません。

承認が有効なのは、提示された正確な質問、プロジェクト、リポジトリ、ブランチ、アーティファクトのフィンガープリント、段階、行為、対象、範囲、環境、そして有効期限に対してのみです。

明確な No は要求された行為を拒否します。

明確な停止または「進めないで」という指示は、その行為を停止します。

## 4. 平易な言葉での承認依頼

承認を依頼する前に、 GARVIS は以下を説明しなければなりません:

1. 提案する行為は何か。
2. 何が変わるのか。
3. 何が変わらないのか。
4. なぜ Adrien の承認が必要なのか。
5. どのファイル、リポジトリ、ブランチ、コミット、アカウント、デバイス、または環境が影響を受けるのか。
6. 無関係なローカル作業が保持されるかどうか。
7. その行為を元に戻せるかどうか。
8. その行為に、インストール、費用、通信、削除、 push、 force-push、マージ、ブランチ削除、デプロイ、ロールバック、 Secrets、または保護対象システムが関わるかどうか。
9. 合格しなければならない正確なチェック項目。
10. 次のコマンドまたは行為を 1 つだけ。

## 5. 開発段階

### 調査

GARVIS は、承認済み情報の確認、要件の特定、リスクの検討、代替案の比較、所見の準備を行ってかまいません。

調査は、実装、インストール、購入、外部との通信、 push、マージ、削除、またはデプロイを許可しません。

### 仕様

GARVIS は、アーキテクチャ、インターフェース、セキュリティルール、テスト、ファイル境界、受け入れ基準、期待される挙動を定義してかまいません。

仕様は、何を作るべきかを記述します。それ自体は本番実装を許可しません。

### プロトタイプ

GARVIS は、承認済みファイル境界の内側でのみ、ローカルの実験的なコードとローカルテストを作成してかまいません。

プロトタイプ作業は、 push、公開、マージ、デプロイ、インストール、購入、または保護対象システムへのアクセスを許可しません。

### テスト

GARVIS は、承認済みの焦点化テストおよびフルテストスイートを実行し、証跡を記録してかまいません。

テスト段階にあると主張している間にコードを変更してはなりません。コード変更は作業をプロトタイプでの修正に戻し、影響を受けたテスト証跡を無効にします。

### セキュリティレビュー

GARVIS は、承認された読み取り専用の分析を、承認、検証、ファイル、ネットワーク利用、コマンド実行、 Secrets、競合状態、副作用、データベース整合性、監査整合性に対して実施してかまいません。

セキュリティ上の失敗は、プロトタイプでの修正に戻さなければなりません。プルリクエストに直接進むことはできません。

### プルリクエスト

プルリクエストは、承認されたブランチを GitHub 上に提示し、自動チェックと人的レビューを実行させます。

プルリクエストの作成や更新は、それ自体をマージしません。

### マージ

マージは、承認済みのプルリクエスト変更を、通常は `main` の宛先ブランチへ取り込みます。

マージ承認はデプロイを許可しません。

### デプロイ

デプロイは、承認済みのアーティファクトを、能動的に動作しうる名前付き環境に配置します。

デプロイには常に、別個の明示的な承認が必要です。

## 6. 実務的な言葉での技術用語

### コミット

コミットは、定義された一群のファイル変更を含む、保存されたローカルチェックポイントです。

コミットを作成しても、 GitHub へ自動的にアップロードされるわけではありません。

### プッシュ

プッシュは、ローカルのコミットを GitHub のブランチへアップロードします。

プッシュはそれらの変更を `main` に配置しません。

### プルリクエスト

プルリクエストは、 GitHub にブランチと宛先ブランチの比較とレビュー用チェックの実行を依頼します。

それはマージではなく、レビュー用のコンテナです。

### スカッシュマージ

スカッシュマージは、プルリクエストの承認済み最終変更を、宛先ブランチ上の 1 つのクリーンなコミットにまとめます。

一時ブランチの履歴は、その 1 つの宛先コミットへと圧縮されます。

### マージコミット

マージコミットは、 2 つのブランチ履歴を結合し、それぞれの個々のコミットを保持します。

### リベースマージ

リベースマージは、個別のマージコミットを作らずに、承認済みブランチの各コミットを宛先ブランチ上に配置します。

### リモートブランチの削除

リモートブランチの削除は、作業がマージされた後に、一時ブランチを GitHub から削除します。

ローカルのブランチやローカルファイルは、ローカル削除が別途説明され承認されない限り削除されません。

### ローカルブランチの削除

ローカルブランチの削除は、デバイスからブランチ名を削除します。

未マージのローカル作業が回復しづらくなる可能性があるため、別個の承認が必要です。

### デプロイ

デプロイは、承認済みコードを、名前付きの運用環境でアクティブにします。

成功したマージは、デプロイ許可を与えません。

### ロールバック

ロールバックは、デプロイまたは保護対象の変更を元に戻します。

ロールバックは保護された行為のままであり、正確に事前承認された緊急ロールバック条件が適用される場合を除き、承認が必要です。

## 7. 保護対象の行為

これらの行為には、それぞれ個別の明示的承認が必要です:

- インストールまたは依存関係の変更
- 購入または金銭的コミットメント
- 電子メール、メッセージング、通知、その他の外部との通信
- ファイル削除
- ローカルブランチの削除
- リモートブランチの削除
- アカウントの変更
- 保護対象システムの変更
- Push
- Force-push
- 実質的なプルリクエストの公開
- マージ
- デプロイ
- ロールバック
- Secret の作成、ローテーション、移転、または開示
- 承認済みサンドボックス外での コンピュータ操作
- 破壊的なデータベース操作
- もとに戻せないマイグレーション

ある段階に入る承認は、その段階内の保護対象の行為を自動的に許可しません。

## 8. 使い切り承認

使い切り承認は 1 回だけ利用できます。

使用後、その承認は消費済みとしてマークされます。

消費済みの承認は再実行できません。

期限切れの承認は拒否されます。

取り消された承認は拒否されます。

質問、ブランチ、範囲、対象、リポジトリ、アーティファクトのフィンガープリント、または環境が変更されると、以前の承認は無効になります。

## 9. 証跡とアーティファクトのフィンガープリント

テストおよびセキュリティの証跡は、レビューされた正確なアーティファクトに結び付けられていなければなりません。

重大なコード変更は、異なるアーティファクトのフィンガープリントを生みます。

以前のアーティファクトの証跡で、変更後のアーティファクトを承認することはできません。

修正後は、影響を受けたすべての下流チェックを繰り返さなければなりません。

## 10. 監査チェーンの保護

ガバナンスの記録は順序で連結されています。

各記録は、直前の記録に結び付いたフィンガープリントを含みます。

ローカルの SQLite ストアも以下を保持します:

- 期待される監査記録数
- 最新の監査フィンガープリント
- 保存されたシーケンス
- プロジェクト履歴
- 承認の質問
- Yes-or-no の決定
- 消費済み承認の状態
- 証跡記録

検証器は、変更された記録、欠落した記録、順序入れ替えられた記録、重複した一次 ID、不一致の参照、変更された最終チェーンアンカーを検出しなければなりません。

付与は元の承認質問を参照してもかまいません。その正当な参照は、質問記録の重複ではありません。

## 11. アトミックな段階変更

承認済みの使い切り承認でプロジェクトが別の段階に移動する際、次の 2 つの事実を同時に保存しなければなりません:

1. 承認が消費された。
2. プロジェクトが承認された宛先段階に入った。

どちらも保存されるか、どちらも保存されないかのいずれかです。

これにより、中断によって承認が未使用のように見える一方でプロジェクトだけが進むことを防ぎます。

## 12. 併行性の保護

複数記録の更新を保存する前に、ストアは、操作開始時に観測した監査チェーンの先頭と現在の先頭を比較します。

もし別の操作が先にストアを変更していた場合、古い操作は停止します。

新しいガバナンス履歴を上書きしてはなりません。

## 13. 現在のプロトタイプ境界

承認済みのプロトタイプには、次の 4 つの実装ファイルが含まれます:

- `src/garvis/stage_gate.py`
- `src/garvis/stage_gate_store.py`
- `tests/garvis/test_stage_gate.py`
- `docs/GARVIS_STAGE_GATE_FOUNDATION.md`

統治用の仕様は以下です:

- `docs/GARVIS_STAGE_GATE_FOUNDATION_SPECIFICATION.md`

無関係な GARVIS のファイルは、承認済みのプロトタイプ境界外にとどまります。

## 14. 現在の制約

このプロトタイプは、まだ次のことを行いません:

- 既存の GARVIS のすべての能力を制御する
- 永続的な本番データベースを有効化する
- すべてのコマンドを自動的にインターセプトする
- GitHub を自動管理する
- 自動的にマージまたはデプロイする
- 依存関係をインストールする
- メッセージを送信する
- 購入を行う
- 保護対象システムを変更する
- 科学的に AGI を実証する
- 人によるレビューを置き換える

GARVIS ランタイム全体との統合には、後続の仕様、プロトタイプ、テスト、セキュリティレビュー、そして個別の承認が必要です。

## 15. 失敗時の取り扱い

完了ゲートの失敗は進行を停止します。

テストの失敗はプロトタイプでの修正に戻します。

セキュリティレビューの失敗はプロトタイプでの修正に戻します。

アーティファクトが変更されると、影響を受けた証跡は無効になります。

壊れた、または検証不能な監査チェーンは、移行または保護対象の行為を阻止します。

段階を完了したように見せるためだけに、エラーを隠してはなりません。
