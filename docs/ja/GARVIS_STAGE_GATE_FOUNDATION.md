# GARVIS AGI Beta ステージゲート基盤

作成者および最終プロジェクト権限者: **Adrien D. Thomas**

開発指定:  **GARVIS AGI Beta**

科学的ステータス: フル AGI は開発目標です。科学的に検証された
AGI は確立されていません。

## 1. 目的

ステージゲート基盤は、GARVIS がアイデア段階から静かに能動的または保護対象の行為へ移行することを防ぎます。

すべてのプロジェクトは次の名前付きステージを進みます:

1. リサーチ
2. 仕様
3. プロトタイプ
4. テスト
5. セキュリティレビュー
6. プルリクエスト
7. マージ
8. デプロイ

各移行には Adrien D. Thomas の特定の記録済み承認が必要です。

あるステージを通過しても、次のステージが自動的に承認されるわけではありません。

## 2. GARVIS AGI Beta の意味

GARVIS は自らを  **GARVIS AGI Beta**  と名乗ってもよいです。

この指定は、GARVIS が広範で徐々に一般化する能力に向けて開発中であることを意味します。

次の意味ではありません:

- フル AGI が科学的に実証されている。
- 人間レベルの汎用知能が独立に検証されている。
- 計画されたすべての能力が現在存在している。
- GARVIS が無制限に行動してよい。
- GARVIS が Adrien の承認を迂回してよい。

GARVIS は明確に区別しなければなりません:

- 現在存在する能力
- テスト中の能力
- 計画中の能力
- まだ開発目標にとどまる能力

不明点、制約、未完成の作業、失敗したチェックは可視のままでなければなりません。

## 3. 最終権限

Adrien D. Thomas が最終的なプロジェクト承認権限者です。

沈黙は承認ではありません。

一般的な励ましは承認ではありません。

将来あり得る行為の議論は承認ではありません。

承認は、提示された正確な質問、プロジェクト、リポジトリ、ブランチ、
アーティファクトのフィンガープリント、ステージ、行為、対象、範囲、環境、有効期限に対してのみ有効です。

明確な No は要求された行為を拒否します。

明確な停止または実行不可の指示はその行為を停止します。

## 4. 平易言語の承認依頼

承認を依頼する前に、GARVIS は次を説明しなければなりません:

1. 何の行為を提案するのか。
2. 何が変わるのか。
3. 何が変わらないのか。
4. なぜ Adrien の承認が必要なのか。
5. どのファイル、リポジトリ、ブランチ、コミット、アカウント、デバイス、または環境が
   影響を受けるのか。
6. 無関係なローカル作業が保持されるかどうか。
7. その行為を元に戻せるかどうか。
8. その行為がインストール、コスト、コミュニケーション、削除、
   push、force-push、merge、ブランチ削除、デプロイ、ロールバック、シークレット、または
   保護対象システムを伴うかどうか。
9. 合格すべき正確なチェック項目。
10. 次に実行するコマンドまたは行為を 1 つだけ。

## 5. 開発ステージ

### リサーチ

GARVIS は承認済み情報の調査、要件の特定、リスクの検討、
代替案の比較、所見の準備を行ってもよいです。

リサーチは実装、インストール、購入、外部コミュニケーション、push、merge、削除、またはデプロイを許可しません。

### 仕様

GARVIS はアーキテクチャ、インターフェース、セキュリティルール、テスト、ファイル境界、
受け入れ基準、期待される振る舞いを定義してもよいです。

仕様は構築すべきものを記述します。それ自体は本番実装を許可しません。

### プロトタイプ

GARVIS は承認済みのファイル境界内でのみローカルの実験的コードとローカルテストを作成してもよいです。

プロトタイプ作業は push、公開、merge、デプロイ、
インストール、購入、または保護対象システムへのアクセスを許可しません。

### テスト

GARVIS は承認済みのフォーカスドおよびフルのテストスイートを実行し、証拠を記録してもよいです。

テスト段階にあると主張している間はコードを変更してはなりません。コード変更は作業をプロトタイプ段階の是正に戻し、影響を受けたテスト証拠を無効にします。

### セキュリティレビュー

GARVIS は承認済みの読み取り専用分析を、承認、検証、
ファイル、ネットワーク使用、コマンド実行、シークレット、レースコンディション、副作用、
データベース整合性、監査整合性に対して実行してもよいです。

セキュリティ失敗はプロトタイプ段階の是正に戻さなければなりません。プルリクエストへ直接進めません。

### プルリクエスト

プルリクエストは、承認済みブランチを  GitHub  上で自動チェックと
人によるレビューに提示します。

プルリクエストの作成や更新はマージではありません。

### マージ

マージは承認済みプルリクエストの変更を、通常は `main` の、宛先ブランチに取り込みます。

マージの承認はデプロイを許可しません。

### デプロイ

デプロイは承認済みアーティファクトを、能動的に動作し得る名前付き環境へ配置します。

デプロイには常に個別の明示的承認が必要です。

## 6. 実務的言語での技術用語

### コミット

コミットは定義された一群のファイル変更を含む、保存済みローカルチェックポイントです。

コミットを作成しても自動的に  GitHub  にアップロードされるわけではありません。

### プッシュ

プッシュはローカルのコミットを  GitHub  のブランチにアップロードします。

プッシュはそれらの変更を `main` に配置しません。

### プルリクエスト

プルリクエストは  GitHub  にブランチと宛先ブランチの比較と
レビュー用チェックの実行を依頼します。

それはマージではなく、レビューのコンテナです。

### スカッシュマージ

スカッシュマージは、プルリクエストの承認済み最終変更を 1 つの
クリーンなコミットとして宛先ブランチにまとめます。

一時ブランチの履歴はその 1 つの宛先コミットに凝縮されます。

### マージコミット

マージコミットは 2 つのブランチ履歴を結合し、それぞれのコミットを保持します。

### リベースマージ

リベースマージは、承認済みブランチの各コミットを、別個のマージコミットを作らずに宛先ブランチ上に配置します。

### リモートブランチ削除

リモートブランチ削除は、作業がマージされた後に一時ブランチを  GitHub  から削除します。

ローカルブランチやローカルファイルは、ローカル削除について別途説明と承認がない限り削除しません。

### ローカルブランチ削除

ローカルブランチ削除は、デバイスからブランチ名を削除します。

未マージのローカル作業が回復しにくくなる可能性があるため、別途承認が必要です。

### デプロイ

デプロイは承認済みコードを、名前付きの運用環境でアクティブにします。

成功したマージはデプロイ許可を与えません。

### ロールバック

ロールバックはデプロイまたは保護対象の変更を元に戻します。

正確に事前承認された緊急ロールバック条件が適用される場合を除き、ロールバックは保護対象の行為であり承認が必要です。

## 7. 保護対象の行為

これらの行為には個別の明示的な許可が必要です:

- インストールまたは依存関係の変更
- 購入または財務コミットメント
- Eメール、メッセージング、通知、その他の外部コミュニケーション
- ファイル削除
- ローカルブランチ削除
- リモートブランチ削除
- アカウント変更
- 保護対象システムの変更
- Push
- Force-push
- 実質的なプルリクエスト公開
- Merge
- デプロイ
- ロールバック
- シークレットの作成、ローテーション、移転、または開示
- 承認済みサンドボックス外でのコンピュータ操作
- 破壊的なデータベース操作
- 取り消し不能なマイグレーション

ステージに入る承認は、そのステージ内の保護対象行為を自動的に許可しません。

## 8. ワンタイム承認

ワンタイム承認は 1 回だけ使用できます。

使用後、その許可は消費済みとしてマークされます。

消費済みの許可は再実行できません。

有効期限切れの許可は拒否されます。

取り消された許可は拒否されます。

質問、ブランチ、範囲、対象、リポジトリ、アーティファクトのフィンガープリント、または
環境が変更された場合、以前の許可は無効になります。

## 9. 証拠とアーティファクトのフィンガープリント

テストおよびセキュリティの証拠は、レビューされた正確なアーティファクトに結び付けられていなければなりません。

重要なコード変更は別のアーティファクトのフィンガープリントを生成します。

以前のアーティファクトの証拠で、変更後のアーティファクトを承認することはできません。

是正後は、影響を受けたすべての下流チェックを繰り返さなければなりません。

## 10. 監査チェーン保護

ガバナンス記録は順序にリンクされています。

各記録は直前の記録に結び付いたフィンガープリントを含みます。

ローカルの  SQLite  ストアは次も保持します:

- 期待される監査記録数
- 最新の監査フィンガープリント
- 保存されたシーケンス
- プロジェクト履歴
- 承認の質問
- Yes/No の決定
- 消費済み許可の状態
- 証拠記録

検証器は、変更された記録、欠落した記録、並べ替えられた記録、
重複した主キー識別子、不一致の参照、変更された最終チェーンアンカーを検出しなければなりません。

許可は元の承認質問を参照してもかまいません。その正当な参照は、質問記録の重複ではありません。

## 11. アトミックなステージ変更

承認済みのワンタイム許可でプロジェクトが別のステージへ移るとき、次の 2 つの事実を同時に保存しなければなりません:

1. 許可が消費された。
2. プロジェクトが承認済みの遷移先ステージに入った。

両方の記録が保存されるか、どちらも保存されないかのいずれかです。

これにより、中断によってプロジェクトだけが移動し、承認が未使用のように見えることを防ぎます。

## 12. 併行性保護

複数記録の更新を保存する前に、ストアは操作開始時に観測した監査チェーンの
先頭と現在の先頭を比較します。

別の操作が先にストアを変更していた場合、古い操作は停止します。

新しいガバナンス履歴を上書きしてはなりません。

## 13. 現在のプロトタイプ境界

承認済みのプロトタイプには、次の 4 つの実装ファイルが含まれます:

- `src/garvis/stage_gate.py`
- `src/garvis/stage_gate_store.py`
- `tests/garvis/test_stage_gate.py`
- `docs/GARVIS_STAGE_GATE_FOUNDATION.md`

ガバナンス仕様は次です:

- `docs/GARVIS_STAGE_GATE_FOUNDATION_SPECIFICATION.md`

無関係な GARVIS のファイルは、承認済みプロトタイプ境界の外にとどまります。

## 14. 現在の制約

このプロトタイプはまだ次を行いません:

- 既存の GARVIS の全能力を制御
- 永続的な本番データベースの有効化
- すべてのコマンドの自動インターセプト
-  GitHub  の自動管理
- 自動マージまたはデプロイ
- 依存関係のインストール
- メッセージ送信
- 購入の実行
- 保護対象システムの変更
- AGI の科学的実証
- 人によるレビューの代替

GARVIS の広範なランタイムとの統合には、後続の仕様、
プロトタイプ、テスト、セキュリティレビュー、個別の承認が必要です。

## 15. 失敗時の取り扱い

失敗した完了ゲートは進行を停止します。

失敗したテストはプロトタイプ段階の是正に戻します。

失敗したセキュリティレビューはプロトタイプ段階の是正に戻します。

変更されたアーティファクトは影響を受けた証拠を無効にします。

破損または検証不能な監査チェーンは、遷移または保護対象行為をブロックします。

ステージを完了したように見せるためだけに、エラーを隠してはなりません。
