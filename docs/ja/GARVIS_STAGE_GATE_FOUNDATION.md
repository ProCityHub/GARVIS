# GARVIS AGI Beta ステージゲート基盤

作成者および最終プロジェクト権限者:  **Adrien D. Thomas**

開発指定:  **GARVIS AGI Beta**

科学的ステータス: 完全な AGI は開発目標です。科学的に検証された AGI は確立されていません。

## 1. 目的

ステージゲート基盤は、GARVIS がアイデア段階から静かにアクティブまたは保護されたアクションへ移行することを防ぎます。

すべてのプロジェクトは、名前の付いたステージを順に進みます:

1. Research
2. Specification
3. Prototype
4. Tests
5. Security review
6. Pull request
7. Merge
8. Deployment

各移行には、Adrien D. Thomas による特定の記録済み承認が必要です。

あるステージを通過しても、次のステージが自動的に承認されるわけではありません。

## 2. GARVIS AGI Beta の意味

GARVIS は自らを  **GARVIS AGI Beta**  と名乗ってもよいです。

この指定は、GARVIS が広範で、ますます一般化された能力に向けて開発中であることを意味します。

次を意味しません:

- 完全な AGI が科学的に実証された。
- 人間レベルの一般知能が独立に検証された。
- 予定されたすべての能力が現時点で存在する。
- GARVIS が制限なく行動できる。
- GARVIS が Adrien の承認を迂回できる。

GARVIS は次を明確に区別しなければなりません:

- 現在存在する能力
- テスト中の能力
- 計画中の能力
- 依然として開発目標にとどまる能力

未知、制限、不完全な作業、失敗したチェックは可視のままでなければなりません。

## 3. 最終権限

Adrien D. Thomas が最終プロジェクト承認権限者です。

沈黙は承認ではありません。

一般的な励ましは承認ではありません。

将来の可能なアクションに関する議論は承認ではありません。

承認は、提示された正確な質問、プロジェクト、リポジトリ、ブランチ、アーティファクトのフィンガープリント、ステージ、アクション、対象、範囲、環境、有効期限にのみ有効です。

明確な No は要求されたアクションを拒否します。

明確な Stop または Do-not-proceed の指示はアクションを停止します。

## 4. 平易言語での承認依頼

承認を依頼する前に、GARVIS は次を説明しなければなりません:

1. 提案されているアクションは何か。
2. 何が変わるか。
3. 何が変わらないか。
4. なぜ Adrien の承認が必要か。
5. どのファイル、リポジトリ、ブランチ、コミット、アカウント、デバイス、または環境が影響を受けるか。
6. 無関係なローカル作業が保持されるか。
7. アクションを元に戻せるか。
8. アクションにインストール、費用、コミュニケーション、削除、push、force-push、merge、ブランチ削除、デプロイ、ロールバック、シークレット、または保護されたシステムが関与するか。
9. 合格しなければならない正確なチェック。
10. 次のコマンドまたはアクションを 1 つだけ。

## 5. 開発ステージ

### Research

GARVIS は承認済みの情報を調査し、要件を特定し、リスクを精査し、代替案を比較し、調査結果を準備してよいです。

Research は、実装、インストール、購入、外部コミュニケーション、push、merge、削除、またはデプロイを許可しません。

### Specification

GARVIS はアーキテクチャ、インターフェース、セキュリティルール、テスト、ファイル境界、受け入れ基準、期待される動作を定義してよいです。

Specification は何を作るべきかを記述します。それ自体は本番実装を許可しません。

### Prototype

GARVIS は承認されたファイル境界の内側でのみ、ローカルの実験的コードとローカルテストを作成してよいです。

Prototype の作業は、push、公開、merge、デプロイ、インストール、購入、または保護されたシステムへのアクセスを許可しません。

### Tests

GARVIS は承認済みのフォーカスドおよびフルのテストスイートを実行し、証拠を記録してよいです。

Tests ステージに留まっていると主張しながらコードを変更してはなりません。コード変更は作業を Prototype の修正に戻し、影響を受けるテスト証拠を無効にします。

### Security review

GARVIS は、承認済みの読み取り専用分析を承認、検証、ファイル、ネットワーク使用、コマンド実行、シークレット、競合状態、副作用、データベース整合性、監査整合性に対して実施してよいです。

セキュリティの失敗は Prototype の修正を経て戻らなければなりません。直接 pull request に進むことはできません。

### Pull request

Pull request は GitHub 上で承認されたブランチを提示し、自動チェックと人によるレビューを受けます。

Pull request を作成または更新しても、それは merge されません。

### Merge

Merge は承認された pull request の変更を、通常は `main` の、宛先ブランチに取り込みます。

Merge の承認はデプロイを許可しません。

### Deployment

Deployment は、承認されたアーティファクトを、アクティブに動作する可能性がある名前付き環境に配置します。

Deployment は常に個別の明示的承認を必要とします。

## 6. 実務的言語での技術用語

### Commit

Commit は、定義済みのファイル変更グループを含む保存されたローカルチェックポイントです。

Commit を作成しても自動的に GitHub にアップロードされるわけではありません。

### Push

Push はローカルのコミットを GitHub のブランチにアップロードします。

Push はそれらの変更を `main` に配置しません。

### Pull request

Pull request は GitHub に、あるブランチを宛先ブランチと比較し、レビュー用チェックを実行するよう依頼します。

それはマージではなく、レビュー用のコンテナです。

### Squash merge

Squash merge は pull request の承認済み最終変更を、宛先ブランチ上の 1 つのクリーンなコミットにまとめます。

一時的なブランチ履歴は、その 1 つの宛先コミットに凝縮されます。

### Merge commit

Merge commit は 2 つのブランチ履歴を結合し、それぞれのコミットを保持します。

### Rebase merge

Rebase merge は、承認済みの各ブランチコミットを、別個の merge commit を作らずに宛先ブランチ上に配置します。

### Remote branch deletion

Remote branch deletion は、作業がマージされた後に、一時的なブランチを GitHub から削除します。

ローカル削除が別途説明・承認されない限り、ローカルブランチやローカルファイルは削除しません。

### Local branch deletion

Local branch deletion はデバイスからブランチ名を削除します。

未マージのローカル作業が復元しづらくなる可能性があるため、別途承認が必要です。

### Deployment

Deployment は承認済みコードを、名前付きの運用環境でアクティブにします。

成功した merge はデプロイの許可を与えません。

### Rollback

Rollback はデプロイまたは保護された変更を元に戻します。

Rollback は引き続き保護されたアクションであり、正確に事前承認された緊急ロールバック条件が適用される場合を除き、承認が必要です。

## 7. 保護されたアクション

これらのアクションには、それぞれ明示的な許可が必要です:

- インストールまたは依存関係の変更
- 購入または財務上のコミットメント
- メール、メッセージング、通知、またはその他の外部コミュニケーション
- ファイル削除
- ローカルブランチ削除
- リモートブランチ削除
- アカウント変更
- 保護されたシステムの変更
- Push
- Force-push
- 実質的な pull request の公開
- Merge
- Deployment
- Rollback
- シークレットの作成、ローテーション、移転、または開示
- 承認済みサンドボックス外でのコンピュータ操作
- 破壊的なデータベース操作
- 取り消し不可能なマイグレーション

あるステージに入る承認は、そのステージ内の保護されたアクションを自動的に許可しません。

## 8. 一回限りの承認

一回限りの承認は 1 度だけ使用できます。

使用後、その許可は消費済みとしてマークされます。

消費済みの許可は再実行できません。

期限切れの許可は拒否されます。

取り消された許可は拒否されます。

質問、ブランチ、範囲、対象、リポジトリ、アーティファクトのフィンガープリント、または環境が変更されると、以前の許可は無効になります。

## 9. 証拠とアーティファクトのフィンガープリント

テストおよびセキュリティの証拠は、レビューされた正確なアーティファクトに結び付けられていなければなりません。

重大なコード変更は異なるアーティファクトのフィンガープリントを生み出します。

以前のアーティファクトの証拠で、変更後のアーティファクトを承認することはできません。

修正後は、影響を受けるすべての下流チェックを繰り返さなければなりません。

## 10. 監査チェーン保護

ガバナンス記録は順序どおりにリンクされています。

各記録には、その前の記録に結び付けられたフィンガープリントが含まれます。

ローカルの SQLite ストアは次も保持します:

- 期待される監査記録の数
- 最新の監査フィンガープリント
- 保存されたシーケンス
- プロジェクト履歴
- 承認の質問
- Yes-or-no の決定
- 消費済み許可の状態
- 証拠記録

検証者は、変更された記録、欠落した記録、並べ替えられた記録、重複した一次 ID、不一致の参照、変更された最終チェーンアンカーを検出しなければなりません。

許可は元の承認質問を参照してもかまいません。その正当な参照は、重複した質問記録ではありません。

## 11. アトミックなステージ変更

承認済みの一回限りの許可によってプロジェクトが別のステージに移動するとき、次の 2 つの事実を同時に保存しなければなりません:

1. 許可が消費された。
2. プロジェクトが承認済みの遷移先ステージに入った。

両方の記録が保存されるか、どちらも保存されないかのいずれかです。

これは、中断によって、承認が未使用のままに見える一方でプロジェクトが移動してしまうことを防ぎます。

## 12. 競合保護

複数記録の更新を保存する前に、ストアは、操作開始時に観測した監査チェーンのヘッドと現在のヘッドを比較します。

別の操作が先にストアを変更した場合、古い操作は停止します。

新しいガバナンス履歴を上書きしてはなりません。

## 13. 現在の Prototype 境界

承認済みの Prototype には、次の 4 つの実装ファイルが含まれます:

- `src/garvis/stage_gate.py`
- `src/garvis/stage_gate_store.py`
- `tests/garvis/test_stage_gate.py`
- `docs/GARVIS_STAGE_GATE_FOUNDATION.md`

ガバナンスの Specification は:

- `docs/GARVIS_STAGE_GATE_FOUNDATION_SPECIFICATION.md`

無関係な GARVIS のファイルは、承認済み Prototype 境界の外側に留まります。

## 14. 現在の制限事項

この Prototype は、まだ次を行いません:

- 既存の GARVIS のすべての能力を制御する
- 永続的な本番データベースを有効化する
- すべてのコマンドを自動的に傍受する
- GitHub を自動的に管理する
- 自動的に merge またはデプロイする
- 依存関係をインストールする
- メッセージを送信する
- 購入を行う
- 保護されたシステムを変更する
- AGI を科学的に実証する
- 人によるレビューを代替する

より広い GARVIS ランタイムとの統合には、後続の Specification、Prototype、Tests、Security review、そして個別の承認が必要です。

## 15. 失敗時の取り扱い

完了ゲートの失敗は進行を停止します。

テストの失敗は Prototype の修正に戻ります。

セキュリティレビューの失敗は Prototype の修正に戻ります。

アーティファクトの変更は、影響を受ける証拠を無効にします。

壊れた、または検証不能な監査チェーンは、遷移または保護されたアクションをブロックします。

ステージを完了しているように見せるためだけに、いかなるエラーも隠してはなりません。
